# Realtime Features

import { Callout } from "nextra/components";

Auktiva supports real-time updates for bids, notifications, and discussions using WebSocket connections. This eliminates the need for constant database polling and provides instant updates to all connected users.

## Architecture

Auktiva uses a **Pusher-compatible** WebSocket protocol, which means you can choose between:

- **Sockudo or Soketi** (self-hosted) - Pusher-compatible servers you run on your own machine.
- **Pusher Channels** (cloud) - Managed realtime service.

Both options use the same client code, so you can switch between them by changing environment variables.

## Setup Options

### Option 1: Self-hosted realtime server

The [stand-alone bundle](https://github.com/thomsa/auktiva/tree/main/deploy/realtime) runs Sockudo behind Caddy with automatic HTTPS and WSS. Use it for a stand-alone server while Auktiva stays on Vercel, or run it on the same VM as Auktiva. The Auktiva driver is called `soketi` for any Pusher-compatible server. Existing Soketi installations and the `soketi:*` npm scripts still work.

#### Prepare the Hetzner VM

1. Start with a small shared-vCPU Hetzner Cloud instance. You can use an existing VM with room for the additional WebSocket connections.
2. Create an A record and, if the VM serves IPv6, an AAAA record for `push.example.org` pointing to the VM.
3. In the Hetzner Cloud Firewall, allow inbound TCP 80 and 443 from the internet and TCP 22 only from your admin IPs. Keep 6001 and 9601 closed on both public interfaces. Docker routes published ports before `ufw` rules, so use the cloud firewall for these restrictions. [Docker firewall documentation](https://docs.docker.com/engine/network/packet-filtering-firewalls/#docker-and-ufw)
4. Install [Docker Engine](https://docs.docker.com/engine/install/) and the Docker Compose plugin. Enable the Docker service on boot.
5. Copy `deploy/realtime/` from the Auktiva checkout to the VM, then create its private environment file:

```bash
cd deploy/realtime
install -m 600 .env.example .env
openssl rand -hex 16
openssl rand -hex 32
```

In `.env`, set `REALTIME_HOSTNAME=push.example.org` and `ACME_EMAIL`. Set `REALTIME_APP_KEY` and `REALTIME_APP_SECRET` to the generated values respectively, and choose a `REALTIME_APP_ID`. Set `REALTIME_ALLOWED_ORIGINS` to the comma-separated list of Auktiva browser origins, for example `https://auctions.example.org`. Include the scheme and any non-default port, with no trailing slash. Keep the file readable only by the deployment user.

Start the bundle and inspect both services:

```bash
docker compose up -d
docker compose ps
curl -fsS https://push.example.org/up
```

Caddy redirects HTTP to HTTPS and manages certificate issuance and renewal. Point an external uptime monitor at `https://push.example.org/up`. Verify from outside the VM that 6001 and 9601 are closed. For troubleshooting, read logs with `docker compose logs --tail=100 realtime caddy` and inspect metrics inside the Sockudo container with `docker compose exec realtime curl -fsS http://127.0.0.1:9601/metrics`.

If nginx or another proxy already handles ports 80 and 443, start only Sockudo with `docker compose --profile no-proxy up -d` and proxy to `127.0.0.1:6001`. Add `--profile no-proxy` to subsequent Compose commands or set `COMPOSE_PROFILES=no-proxy` in the bundle’s `.env`. The service in this profile is named `realtime-local`. See the [nginx configuration](/developers/deployment#websocket-server-soketi-or-sockudo).

Use Docker Engine 28 or newer for the no-proxy profile on a production VM. Earlier versions can expose localhost-published ports to hosts on the same network segment. [Docker port publishing documentation](https://docs.docker.com/engine/network/port-publishing/)

#### Verify the server

On a workstation with the Auktiva checkout and its npm dependencies installed, set `SOKETI_APP_ID`, `NEXT_PUBLIC_SOKETI_APP_KEY`, and `SOKETI_APP_SECRET` in your local environment or Auktiva `.env`. Use an origin from the bundle’s `REALTIME_ALLOWED_ORIGINS` list:

```bash
npm run realtime:smoke -- --host push.example.org --port 443 --tls true --origin https://auctions.example.org
```

The check signs a private subscription, publishes a test event, and waits up to 10 seconds for its payload. It prints the round-trip time on success and names the failed step on error. Use `SOKETI_APP_SECRET` for production credentials to keep the secret out of command history and npm’s command output.

#### Configure Auktiva on Vercel

Set these values in Vercel’s Production environment. Use the same ID, key, and secret configured in the bundle:

```dotenv
NEXT_PUBLIC_REALTIME_DRIVER=soketi
NEXT_PUBLIC_SOKETI_APP_KEY=your-app-key
NEXT_PUBLIC_SOKETI_HOST=push.example.org
NEXT_PUBLIC_SOKETI_PORT=443
NEXT_PUBLIC_SOKETI_USE_TLS=true
SOKETI_APP_ID=auktiva
SOKETI_APP_SECRET=your-app-secret
SOKETI_HOST=push.example.org
```

Both Vercel and browsers connect over TLS on port 443. For a co-located Auktiva server that can reach Sockudo on the private network, set `SOKETI_HOST` to the internal service address, `SOKETI_PORT=6001`, and `SOKETI_USE_TLS=false`. Leave the public browser host, port, and TLS settings on the Caddy or nginx endpoint.

Keep the Pusher credentials available for rollback. Cut over during a quiet window with no items closing soon. In the Vercel dashboard, select a production deployment, choose **Redeploy**, and clear **Use existing Build Cache**. The change needs a rebuild because the browser connection settings and CSP are set at build time. Tabs opened before the cutover keep their previous provider until reloaded. [Vercel deployment instructions](https://vercel.com/docs/deployments/troubleshoot-a-build#managing-build-cache)

After the redeploy, open the same item in two browser sessions and check that a bid appears live, the outbid notification count updates, and the WebSocket connects to `push.example.org` without a CSP error. To roll back, set `NEXT_PUBLIC_REALTIME_DRIVER=pusher` and redeploy without the build cache.

#### Update and rotate credentials

Update by changing the pinned image reference in `deploy/realtime/docker-compose.yml`, then running `docker compose pull` and `docker compose up -d` on the VM. Repeat the health and smoke checks after the update. The bundle pins an official Sockudo build by digest until the first stable release with the upstream private-channel security fixes is available. [Sockudo image pin](https://github.com/thomsa/auktiva/blob/main/deploy/realtime/README.md)

To rotate the secret, change `REALTIME_APP_SECRET` in the VM’s `.env` and `SOKETI_APP_SECRET` in Vercel’s Production environment. Recreate the service with `docker compose up -d` and redeploy Auktiva. Schedule the change in a quiet window because private subscription authorization can fail while the two values differ. Run the smoke check with the new secret and check live updates in both browser sessions.

### Option 2: Pusher Channels (Cloud)

Pusher Channels is a managed WebSocket service. The free tier includes:

- 200,000 messages/day
- 100 concurrent connections
- Unlimited channels

#### Setup

1. Create a free account at [pusher.com](https://pusher.com)
2. Create a new Channels app
3. Copy your credentials

#### Configuration

```bash
# Shared config (used by both server and client)
NEXT_PUBLIC_REALTIME_DRIVER="pusher"
NEXT_PUBLIC_PUSHER_KEY="your-app-key"
NEXT_PUBLIC_PUSHER_CLUSTER="eu"  # or us2, ap1, etc.

# Server-only config (not exposed to browser)
PUSHER_APP_ID="your-app-id"
PUSHER_SECRET="your-app-secret"
```

### Option 3: Disabled (Polling Fallback)

Set `NEXT_PUBLIC_REALTIME_DRIVER=disabled` or leave realtime unconfigured to use polling. When realtime is enabled, the app polls at its normal intervals while the WebSocket is disconnected. The browser retries automatically and stops polling when it reconnects. The item page, discussions, and notifications then refetch once to catch up on missed events.

Polling intervals:

- Critical (item detail page): 2 seconds
- High (auction pages): 5 seconds
- Medium (dashboard): 15 seconds
- Low (other pages): 30 seconds

## Event Types

All events are sent on private channels that require authentication.

### Item Events

| Event                | Channel                 | Description                                                       |
| -------------------- | ----------------------- | ----------------------------------------------------------------- |
| `bid:new`            | `private-item-{itemId}` | New bid placed                                                    |
| `item:updated`       | `private-item-{itemId}` | Item changed, for example reopened (`changes: { endDate: null }`) |
| `discussion:new`     | `private-item-{itemId}` | New comment posted                                                |
| `discussion:deleted` | `private-item-{itemId}` | Comment deleted                                                   |

<Callout type="info">
  `item:updated` is published when bidding reopens on an item and when a member
  leaves or is removed and their bids are deleted. No client page subscribes to
  it yet, so an open item page shows a reopened item as closed until it is
  reloaded. Bidding-reopened and win notifications reach users through
  `notification:new` and `notification:count`, like every other notification.
</Callout>

### User Events

| Event                | Channel                 | Description          |
| -------------------- | ----------------------- | -------------------- |
| `bid:outbid`         | `private-user-{userId}` | User was outbid      |
| `notification:new`   | `private-user-{userId}` | New notification     |
| `notification:count` | `private-user-{userId}` | Unread count updated |

### Auction Events

| Event          | Channel                       | Description         |
| -------------- | ----------------------------- | ------------------- |
| `item:created` | `private-auction-{auctionId}` | New item in auction |

## Security

### Channel Types

**All channels in Auktiva are private** and require authentication. This ensures that only authorized users can receive realtime updates.

| Channel                       | Who Can Subscribe                  |
| ----------------------------- | ---------------------------------- |
| `private-user-{userId}`       | Only the user with matching ID     |
| `private-auction-{auctionId}` | Only members of the auction        |
| `private-item-{itemId}`       | Only members of the item's auction |

### Authentication Flow

Private channels use Pusher's authentication protocol:

1. Client attempts to subscribe to `private-user-abc123`
2. Pusher client automatically calls `/api/pusher/auth` with socket ID and channel name
3. Server validates:
   - User is logged in (NextAuth session)
   - User has permission for this channel (e.g., `userId === channelUserId`)
4. Server signs the auth response with `SOKETI_APP_SECRET` (HMAC-SHA256)
5. Client presents signed auth to Soketi/Pusher
6. Soketi/Pusher verifies signature and allows subscription

### Authorization Rules

| Channel Pattern               | Who Can Subscribe                  |
| ----------------------------- | ---------------------------------- |
| `private-user-{userId}`       | Only the user with matching ID     |
| `private-auction-{auctionId}` | Only members of the auction        |
| `private-item-{itemId}`       | Only members of the item's auction |

### Security Best Practices

1. **Keep secrets secure** - Never expose `SOKETI_APP_SECRET` or `PUSHER_SECRET` to the client
2. **Use TLS in production** - Set `NEXT_PUBLIC_SOKETI_USE_TLS="true"` for encrypted connections
3. **Validate all channel access** - The auth endpoint checks permissions before signing
4. **Don't trust client data** - Event payloads are generated server-side, not from client input

### What Users Can See

- **Their own notifications** - Only via `private-user-{theirId}`
- **Auction events** - Only if they're a member of that auction
- **Item events (bids, discussions)** - Only if they're a member of the item's auction

Users **cannot**:

- Subscribe to other users' private channels
- Access auction or item channels without membership
- Forge authentication (requires server-side secret)

## Troubleshooting

### Self-hosted server is unreachable

Check the external HTTPS health URL and the container state with `docker compose ps`. For nginx or the local profile, check `http://127.0.0.1:6001/up` from the VM or workstation. If the service is healthy, check that the hostname and TLS port match `NEXT_PUBLIC_SOKETI_HOST` and `NEXT_PUBLIC_SOKETI_PORT`. Confirm that the application’s browser origin appears in `REALTIME_ALLOWED_ORIGINS` and that the app credentials match the bundle. See [Troubleshooting](/developers/troubleshooting) for common configuration errors.

### Debug WebSocket connections

Enable debug logging to see connection details:

**Server-side:** Add `REALTIME_DEBUG="true"` to `.env` and restart

**Client-side:** In browser console, run:

```javascript
localStorage.setItem("REALTIME_DEBUG", "true");
```

Then refresh the page and check console for `[Realtime:Client]` logs.

### Pusher limit exceeded

If you see "PUSHER LIMIT EXCEEDED" in logs:

- Consider upgrading your Pusher plan
- Switch to self-hosted Soketi
- The app will automatically fall back to polling

### Private channel auth fails

Private channels require authentication. Check:

1. User is logged in
2. `/api/pusher/auth` endpoint is accessible
3. User has permission to access the channel (e.g., auction member)

## Local Development

### Quick Start

Start the same Sockudo image used by the VM bundle, then start Auktiva with the development settings below:

```bash
npm run realtime:local
curl -fsS http://127.0.0.1:6001/up
npm run --silent realtime:smoke -- --host 127.0.0.1 --port 6001 --tls false --app-id auktiva --key dev-key --secret dev-secret --origin http://localhost:3000
npm run dev
```

Sockudo listens on loopback and accepts the `http://localhost:3000` browser origin. Set `REALTIME_ALLOWED_ORIGINS` before starting Sockudo if you use a different local origin. Use `npm run realtime:local -- down` to remove the local containers. The existing `npm run dev:realtime` command starts Soketi alongside Next.js.

### Environment Variables for Development

Create or update your `.env` file with these development settings:

```bash
# Shared config (used by both server and client)
NEXT_PUBLIC_REALTIME_DRIVER="soketi"
NEXT_PUBLIC_SOKETI_APP_KEY="dev-key"
NEXT_PUBLIC_SOKETI_PORT="6001"
NEXT_PUBLIC_SOKETI_USE_TLS="false"

# Server-only config
SOKETI_APP_ID="auktiva"
SOKETI_APP_SECRET="dev-secret"
SOKETI_HOST="127.0.0.1"

# Client-only config (for local dev, can be localhost)
NEXT_PUBLIC_SOKETI_HOST="127.0.0.1"

# Enable debug logging (optional, enabled by default in development)
REALTIME_DEBUG="true"
```

### Debug Logging

Debug logs are **automatically enabled** in development mode (`NODE_ENV=development`).

**Server-side logs** appear in your terminal:

```
[Realtime:Server] Initializing Pusher client { driver: 'soketi', host: '127.0.0.1', port: 6001 }
[Realtime:Server] Publishing: bid:new → item-abc123 { ... }
[Realtime:Server] Published successfully: bid:new → item-abc123
```

**Client-side logs** appear in browser DevTools console (purple color):

```
[Realtime:Client] Initializing Pusher client { driver: 'soketi', wsHost: '127.0.0.1', wsPort: 6001 }
[Realtime:Client] Connection state: initialized → connecting
[Realtime:Client] Connection state: connecting → connected
[Realtime:Client] Connected successfully!
[Realtime:Client] Subscribing to channel: private-user-xyz789
[Realtime:Client] Subscribed to channel: private-user-xyz789
[Realtime:Client] Received event: notification:new { ... }
```

To enable debug logging in production or disable in development:

- **Server**: Set `REALTIME_DEBUG="true"` or `"false"` in `.env`
- **Client**: Run `localStorage.setItem('REALTIME_DEBUG', 'true')` in browser console

### Running Soketi Separately

If you prefer to run Soketi in a separate terminal:

```bash
# Terminal 1: Start Soketi with debug logging
npm run soketi:dev

# Terminal 2: Start Next.js
npm run dev
```

### Manual Soketi Start

For more control over Soketi options:

```bash
# With debug logging
SOKETI_DEBUG=true soketi start

# With custom port
SOKETI_PORT=6002 soketi start

# With custom credentials
SOKETI_DEFAULT_APP_ID=myapp \
SOKETI_DEFAULT_APP_KEY=mykey \
SOKETI_DEFAULT_APP_SECRET=mysecret \
soketi start
```
