# Deployment

This guide covers deploying Auktiva to various environments.

import { Callout } from "nextra/components";

## Deployment Options

| Platform     | Database        | Storage     | Difficulty |
| ------------ | --------------- | ----------- | ---------- |
| VPS with PM2 | SQLite or Turso | Local or S3 | Easy       |
| Docker       | SQLite or Turso | Local or S3 | Easy       |
| Vercel       | Turso only      | S3 only     | Easy       |

<Callout type="warning">
  Serverless platforms (Vercel, Netlify) require Turso database and S3 storage.
  SQLite and local storage won't work due to ephemeral filesystems.
</Callout>

## Docker Deployment (Recommended)

The easiest way to deploy Auktiva is using Docker with the included `docker-compose.yml`.

### Prerequisites

- Docker and Docker Compose installed
- A domain name (optional, for HTTPS)

### Quick Start

```bash
# Clone the repository
git clone https://github.com/thomsa/auktiva.git
cd auktiva

# Create environment file
cp .env.example .env

# Generate secrets
AUTH_SECRET=$(openssl rand -base64 32)
SOKETI_APP_KEY=$(openssl rand -hex 16)
SOKETI_APP_SECRET=$(openssl rand -hex 32)

# Edit .env with your settings
nano .env
```

### Environment Variables

See [Environment Variables](/developers/environment-variables) for a complete reference of all configuration options.

**Minimum required for Docker:**

```bash
# Authentication (REQUIRED)
AUTH_SECRET="your-generated-secret"
AUTH_URL="https://auctions.yourdomain.com"

# Realtime (optional but recommended)
NEXT_PUBLIC_REALTIME_DRIVER="soketi"
NEXT_PUBLIC_SOKETI_APP_KEY="your-generated-key"
SOKETI_APP_SECRET="your-generated-secret"
NEXT_PUBLIC_SOKETI_HOST="auctions.yourdomain.com"
```

### Start with Docker Compose

```bash
# Build and start all services
docker compose up -d

# View logs
docker compose logs -f

# Stop services
docker compose down
```

This starts:

- **auktiva** - The main application on port 3000
- **soketi** - WebSocket server for realtime features on port 6001

### Data Persistence

Docker volumes are used to persist data:

- `auktiva-data` - SQLite database
- `auktiva-uploads` - Uploaded images
- `auktiva-logs` - Application logs

### Building Manually

If you prefer to build the image manually:

```bash
# Build the image
docker build -t auktiva .

# Run the container
docker run -d \
  --name auktiva \
  -p 3000:3000 \
  -e AUTH_SECRET="your-secret" \
  -e AUTH_URL="http://localhost:3000" \
  -e DATABASE_URL="file:./data/auktiva.db" \
  -v auktiva-data:/app/data \
  -v auktiva-uploads:/app/public/uploads \
  auktiva
```

## VPS Deployment (PM2)

Deploy directly to a VPS without Docker using PM2 process manager.

### Step 1: Install Dependencies

```bash
# Install Node.js 20
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs

# Install PM2 globally
sudo npm install -g pm2
```

### Step 2: Clone and Setup

```bash
git clone https://github.com/thomsa/auktiva.git
cd auktiva
npm ci
npm run setup
```

### Step 3: Build and Start

```bash
npm run build
pm2 start ecosystem.config.js
pm2 save
pm2 startup
```

## Nginx Reverse Proxy

For both Docker and PM2 deployments, use Nginx as a reverse proxy.

### Main Application

```nginx
server {
    listen 80;
    server_name auctions.yourdomain.com;

    location / {
        proxy_pass http://localhost:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}
```

### WebSocket Server (Soketi or Sockudo)

Use a separate hostname for the realtime server. If nginx already handles 80 and 443 on the VM, use the [stand-alone bundle’s no-proxy profile](/developers/realtime#prepare-the-hetzner-vm):

```bash
cd deploy/realtime
docker compose --profile no-proxy up -d
```

This serves the WebSocket and signed publish API on `127.0.0.1:6001`. An existing Soketi instance can use the same nginx configuration if it listens there. Obtain the TLS certificate before installing the HTTPS block. If the hostname is new, add a temporary nginx HTTP site for it, reload nginx, and run `sudo certbot certonly --nginx -d ws.auctions.yourdomain.com`.

```nginx
map $http_upgrade $realtime_connection {
    default upgrade;
    '' close;
}

server {
    listen 80;
    server_name ws.auctions.yourdomain.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name ws.auctions.yourdomain.com;
    ssl_certificate /etc/letsencrypt/live/ws.auctions.yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ws.auctions.yourdomain.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:6001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $realtime_connection;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 86400;
    }
}
```

Check and reload nginx with `sudo nginx -t` and `sudo systemctl reload nginx`. Set `NEXT_PUBLIC_SOKETI_HOST=ws.auctions.yourdomain.com`, `NEXT_PUBLIC_SOKETI_PORT=443`, and `NEXT_PUBLIC_SOKETI_USE_TLS=true` in Auktiva. If the app server also runs on the VM, set its internal `SOKETI_HOST=127.0.0.1`, `SOKETI_PORT=6001`, and `SOKETI_USE_TLS=false`.

### Enable HTTPS

```bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d auctions.yourdomain.com
```

## Vercel Deployment

<Callout type="info">
  Vercel requires Turso database and S3 storage due to its serverless nature.
</Callout>

1. Push your code to GitHub
2. Import project in Vercel Dashboard
3. Set environment variables (see [Configuration](/developers/configuration))
4. Deploy

The repository's `vercel.json` sets the build command to
`prisma generate && npx tsx scripts/migrate-turso.ts && npx tsx prisma/seed-currencies.ts && next build`.
Every Vercel build therefore applies pending migrations to the Turso
database in `DATABASE_URL`, and seeds currencies when that table is empty,
before it runs `next build`. The previous deployment keeps serving until the
new one is live. `vercel.json` also turns off Git deployments, so production
deploys come from the deploy hook that the tag workflow
(`.github/workflows/vercel-release.yml`) calls. See
[Upgrading](/developers/upgrading) for release-specific steps.

<Callout type="warning">
  Rate limiting uses in-memory storage which doesn't work reliably on Vercel.
  Consider using Upstash Redis for production rate limiting.
</Callout>

### Vercel app + self-hosted realtime server

Keep the Auktiva app on Vercel and run the [realtime VM bundle](/developers/realtime#prepare-the-hetzner-vm) at a dedicated HTTPS hostname. Configure the Vercel functions to publish over HTTPS and browsers to connect over WSS on port 443. Follow the [Vercel cutover and rollback instructions](/developers/realtime#configure-auktiva-on-vercel).

## Releasing

Maintainers cut releases of the hosted instance with the release script:

```bash
npm run release -- <patch|minor|major|X.Y.Z> [--dry-run]
```

The script fetches `origin` (including tags) and refuses to continue unless:

- the working tree is clean, with no uncommitted changes or untracked files
- `HEAD` is exactly `origin/main`. It works from a detached `HEAD` or a
  linked worktree, so `git switch --detach origin/main` is enough
- the tag `vX.Y.Z` does not exist locally or on `origin`
- an explicit `X.Y.Z` is a valid semantic version greater than the current
  version

It then sets the version in `package.json` and `package-lock.json`, commits
`chore: release vX.Y.Z`, creates the annotated tag `vX.Y.Z`, and pushes both
in one atomic push:

```bash
git push --atomic --no-follow-tags origin HEAD:refs/heads/main refs/tags/vX.Y.Z
```

The push updates both refs or neither. If it fails, the script prints how
to retry it or how to undo the local commit and tag. `--dry-run` runs every
check, including the fetch and the remote tag lookup, and prints the next
version and the exact commands without changing anything. Pass it after
`--`. If npm takes `--dry-run` for itself (`npm run release patch --dry-run`),
the script warns and still only does a dry run.

The push goes directly to `refs/heads/main`, so `main`'s GitHub rules must
allow it. Rulesets that require pull requests or signed commits reject the
push unless the person pushing has bypass rights, and the atomic push then
publishes nothing.

The pushed tag starts two workflows:

- **Vercel Production Deploy on Tag** (`.github/workflows/vercel-release.yml`)
  calls the app deploy hook, and the docs deploy hook when `docs/` changed
  since the previous tag. Both hooks build the current head of `main`, not the
  tag, so the workflow fails unless the tag commit is the head of
  `origin/main`. Main can still move between that check and the Vercel build,
  so avoid merging to `main` while a release deploys.
- **Release** (`.github/workflows/release.yml`) publishes the release notes,
  generated with git-cliff, as a
  [GitHub Release](https://github.com/thomsa/auktiva/releases).

Release notes live in GitHub Releases. `CHANGELOG.md` is no longer updated.

## Updates

### Docker

```bash
cd /path/to/auktiva
git pull
docker compose build
docker compose up -d
```

### PM2

```bash
cd /path/to/auktiva
git pull
npm ci
npm run build
pm2 restart auktiva
```

Or use the built-in update system from Settings → Deployment Administration (see [Deployment Admin](/developers/deployment-admin)).
